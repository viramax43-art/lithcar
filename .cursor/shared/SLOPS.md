# SLOPS.md — как не порождать архитектурный slop

Инструкции агенту (и человеку) по предотвращению классов ошибок, которые копятся,
когда код много раз переписывают под новые флоу. Правила **универсальные** — применимы
к любому проекту. Каждый пункт: **антипаттерн → почему больно → как правильно**.
Примеры иллюстративные, без привязки к конкретному репозиторию.

Главный принцип: **инвариант, который держится только на дисциплине/комментарии,
не держится.** Делай инварианты структурно неизбежными, а не задокументированными.

---

## Базовые принципы слоёв (Clean Architecture — прагматично)

Это **ориентир**, не обязательная структура папок. SLOPS не требует `routers/` +
`services/` + `repositories/` в каждом проекте — требует **направление зависимостей**
и **разделение ответственности**. Конкретные § ниже — частные случаи этих правил.

### Правило зависимостей

**Внутренние слои не знают о внешних.** Бизнес-правила не импортируют FastAPI,
SQLAlchemy session, Telethon, HTTP-статусы, формат JSON ответа. Внешний слой вызывает
внутренний — never наоборот.

*Проверка:* если удалить HTTP/worker/БД, доменный модуль всё ещё компилируется и
тестируется без моков фреймворка.

### Четыре слоя (упрощённо)

| Слой | Что делает | Не делает |
|------|------------|-----------|
| **Domain** | Инварианты, enum статусов, правила «можно/нельзя», чистые функции над сущностью | SQL, `Request`, commit, формат API |
| **Application (use cases)** | Сценарий: «опубликовать черновик», «пометить канал» — оркестрация domain + порты | Декораторы роутов, inline dict для UI |
| **Adapters** | HTTP-handlers, worker tick, репозиторий/ORM-запросы, Telegram-клиент | Новые бизнес-правила «на месте» |
| **Frameworks** | FastAPI, Postgres, Redis, Docker — детали доставки | — |

Имена пакетов могут быть любыми (`comment_publish.py`, `channel_protection.py`) —
важно, **какой слой внутри файла**, а не название папки.

### Тонкий край, толстый центр

**Антипаттерн (fat adapter).** Handler на 200 строк: auth, SQL, бизнес-ветвление,
сборка JSON, commit — всё в `@app.get`. Worker-тick с той же логикой, скопированной
иначе (§4, §5).

**Как правильно.**
- **Handler / worker hook** — parse input, вызвать use case, map result → HTTP/DTO,
  обработать известные ошибки → status code.
- **Use case / domain module** — решение; принимает типы домена и порты (session,
  clock), не знает про dashboard.js.
- **Один билдер wire-формы** на сущность (`serialize_post`, `*_ui_payload`) — §44;
  handler не собирает dict полями вручную.

### Порты и адаптеры (не обязательно «Repository» везде)

Порт — **интерфейс потребности** use case («сохранить черновик», «отложить publish»).
Адаптер — реализация через ORM/Telegram/файл.

- Не плодить `IUserRepository` ради церемонии, если use case один и ORM уже изолирован
  в одном модуле.
- Плодить порт **имеет смысл**, когда один сценарий вызывается из API **и** worker **и**
  теста — общий use case, разные адаптеры входа (§5).

### DTO на границе

- **Domain** оперирует сущностью/enum, не «JSON для фронта».
- **Wire DTO** (dict/pydantic) — только на границе adapter → клиент; UI-тексты бейджей
  из серверного словаря по enum, не regex по `reason` (§50).
- Свободный текст (`last_error`, `publish_error`) — detail для оператора, не классификация
  статуса (§7).

### Что не делать (over-engineering)

- Не разносить каждый эндпоинт в свой «service class» с одним методом — достаточно
  функции use case в доменном модуле.
- Не вводить слой «ради Clean Architecture», если god-файл можно сначала распилить
  на **feature-модули + serialize_*** без полной перестройки (§3).
- Рефакторинг слоёв — **механический и по частям**: сначала вынести serialize/use case,
  потом router; поведение не менять без явного запроса (§12).

### Связь с пунктами SLOPS

| Принцип CA | Пункты SLOPS |
|------------|--------------|
| Один SoT, domain не stringly-typed | §1, §2 |
| God-файл = смешение слоёв | §3 |
| API и worker делят use case | §4, §5 |
| Один DTO на сущность | §44 |
| UI из enum, не из текста БД | §50 |
| «Latest per group» — SQL window, не full scan | §51 |
| Auth на границе adapter | §43 |

*Иллюстрация (любой стек):* `POST /drafts/{id}/publish` → handler 15 строк →
`publish_draft(session, draft_id)` в application-модуле → `serialize_draft(draft)` для
ответа; worker в том же `publish_draft`, другой adapter входа.

## 1. Фиктивный «единый источник правды» (declared, not enforced)

**Антипаттерн.** Модуль объявляет себя SoT в докстринге («здесь все значения X»),
но по факту часть значений — голые литералы в других файлах, или «каноническая»
функция имеет 1 живой вызов, пока горячий путь идёт мимо.
*Примеры:* модуль `statuses.py` объявлен «единственным источником статусов», но из
~14 значений в enum только 4, остальные — строковые литералы в handlers. Функция
`run_operation()` подана как «единая дверь» для всех операций — 1 вызов в проде,
основной путь идёт мимо.

**Почему больно.** Хуже, чем честное отсутствие SoT: даёт ложную уверенность
(«всё централизовано»), а на деле при изменении надо править N мест, которые уже
разошлись. Ревьюер верит докстрингу, а не коду.

**Как правильно.**
- SoT — это **код, который невозможно обойти**, а не комментарий. Enum вместо строк,
  общая функция-предикат вместо копий условий, один конструктор вместо inline-сборки.
- Если пишешь в комментарии «должно совпадать с X» / «keep in sync with X» — это
  сигнал вынести общий код, а не оставить два пути (см. §5).
- Прежде чем верить «это единый источник», грепни реальные вызовы/литералы.

## 2. Stringly-typed доменные значения

**Антипаттерн.** Статусы/типы/режимы как голые строковые литералы (`"ok"`, `"pending"`,
`"approved"`) разбросаны по коду; наборы допустимых значений продублированы в нескольких
местах и тихо расходятся. Часто рядом сосуществуют константа и голый литерал того же
значения — split-brain в одном файле.

**Почему больно.** Опечатка не ловится типами. Изменение значения = правка в 20 местах.
`grep` не находит все места (литерал vs константа vs SQL-строка). Наборы расходятся.

**Как правильно.**
- Один `Enum`/`StrEnum` (для значений в БД — `StrEnum`: член равен своей строке, кладётся
  в колонку и в SQL без изменений — миграция литералов **не меняет поведения**).
- Ноль голых литералов статуса в коде. Наборы (`frozenset`) — из членов enum, в одном месте.
- **Осторожно с общим именем атрибута.** Если поле называется `.status` у пяти разных
  моделей с разными наборами значений — слепая замена по `\.status ==` испортит чужие
  статусы. Мигрируй по уникальному имени поля или с анализом типа переменной, не блайндом.

## 3. God-файлы и god-функции

**Антипаттерн.** Файл на 5000 строк с ~10 ответственностями; функция на 1000+ строк;
вложенные функции с `nonlocal`, разделяющие скрытое состояние; вложенность на 16 пробелов.
*Пример:* оркестратор-воркер, где две функции обработки одной сущности = 40%+ файла.

**Почему больно.** Невозможно протестировать иначе как грепом по исходнику (см. §8).
`nonlocal` = скрытое разделяемое состояние → гонки. Любая правка рискует задеть соседнюю
ответственность. Контекст не помещается в голову/окно.

**Как правильно.**
- Одна ответственность на модуль. Функция > ~100 строк или вложенность > 3 — кандидат на
  вынос. Вложенная функция, которая большая или переиспользуемая, → на уровень модуля.
- Разделяемое мутируемое состояние → **явный объект** (dataclass), передаваемый параметром,
  а не `nonlocal`/замыкание. Read-only захваты — тоже в явный ctx-объект.
- Вынос делай механически и проверяемо: сначала расплети (dedent + explicit state),
  тестозелёно, потом переноси в отдельный модуль.

## 4. Копипаст-логика, которая расходится

**Антипаттерн.** Один и тот же блок (сброс в очередь, WHERE-условия, guard 404,
нормализация timezone, `utcnow`) скопирован в N местах. Со временем копии расходятся —
одна чистит поле, другая нет.
*Примеры:* «reset entity → pending» в 5 местах, две версии уже чистили разные поля
(потенциальный баг stale-поля). Хелпер `utcnow()` — 10+ идентичных копий в разных модулях.

**Почему больно.** Правишь одно — забываешь остальные. Расхождение = баг, который
виден только на конкретном пути.

**Как правильно.**
- Копируешь блок 2-й раз → выноси в хелпер **сразу**.
- Периодически ищи «почти одинаковые» функции по разным модулям и своди в один источник.
- Формулу/условие, ведомые в двух представлениях (код и SQL), либо сведи, либо покрой
  тестом-эквивалентности — иначе тихо разойдутся.

## 5. Ручная синхронизация комментарием

**Антипаттерн.** Два пути (например read-model в API и в воркере) с комментарием
«держите в синхроне с X» вместо общего кода.
*Пример:* запрос списка в dashboard с пометкой «совпадает с воркером» — на деле
уже разошёлся (не фильтровал soft-deleted записи или не учитывал тот же scope).

**Почему больно.** Люди не удерживают два пути в синхроне усилием воли. Они **гарантированно**
разойдутся, и это read-model → тихий неверный показ, который заметят не сразу.

**Как правильно.** Один источник кода (функция, возвращающая условия/DTO), вызываемый
из обоих мест. Комментарий «должно совпадать» = TODO на извлечение, не решение.

## 6. Миграции и self-heal, прибитые в горячий путь навсегда

**Антипаттерн.** Одноразовые миграции данных / backfill / `_heal_legacy_*`, запускаемые
на **каждом старте** или **каждом цикле** воркера, и живущие там годами.

**Почему больно.** Растят latency и когнитивную нагрузку; «легаси» становится неудаляемым
(никто не знает, безопасно ли убрать); маскируют реальный долг под «self-healing».

**Как правильно.**
- Разовые миграции — отдельный шаг/CLI, не hot-path. Логируй `rowcount`; когда стабильно
  `0` N дней — удаляй.
- Self-heal, который обязан крутиться, — выноси в явный maintenance-модуль с интервалом,
  не подмешивай в основной цикл обработки.
- Помечай временный код условием ретайра («удалить после Y»), а не просто словом `legacy`.

## 7. Классификация ошибок по подстроке

**Антипаттерн.** Функция `is_network_error()`, матчащая 25 подстрок в тексте исключения, плюс
«любой `OSError`/`ConnectionError` → сеть → бесконечный ретрай». Строковая проверка
`"database is locked"` с фейковой простановкой `status="ok"`.

**Почему больно.** Заглатывает НЕ-сетевые баги в вечный ретрай; маскирует реальные сбои под
«здоров». Текст исключений меняется между версиями библиотек — матчинг молча ломается.

**Как правильно.** Классифицируй по **типу исключения**, не по тексту. Неизвестное — не
глотай в retry-петлю: пробрось или залогируй как неизвестное. `except Exception: pass` без
ре-райза — красный флаг.

---

## 8. Хрупкие тесты, проверяющие текст исходника

**Антипаттерн.** Тест делает `Path("module.py").read_text()` и `assert "literal" in source`
или бьётся об **точный отступ** (`"\n                except "`). Любой рефакторинг (переименование,
dedent, вынос) ломает такой тест, хотя поведение не изменилось.

**Почему больно.** Тест проверяет форму, а не поведение. Он и не ловит реальные баги, и
блокирует безопасный рефакторинг (а иногда молча «проходит» из-за случайной границы блока).

**Как правильно.** Тестируй **поведение** через публичный API (вызови функцию, проверь
результат/побочный эффект). Если структуру всё же нужно проверить — делай это устойчиво
к отступам/именам (парси по одному отступу с найденным, а не хардкодь пробелы) и ссылайся
на актуальный источник, а не на скопированный литерал.

## 9. Naming-хаки вместо структуры

**Антипаттерн.** Смысл закодирован в имени переменной: `inner_session` vs `session` (чтобы не
конфликтовать при вложенности), роль клиента — строкой, идентификатор — путём к файлу
без расширения (расширение доклеивается вручную везде).

**Почему больно.** «Правильное имя» — не гарантия; при рефакторинге вложенности легко получить
`inner_inner_session`/`NameError`. Смысл, размазанный по конвенции имён, невозможно проверить.

**Как правильно.** Кодируй смысл **структурой**: контекст-менеджер владеет транзакцией/сессией;
типизированный объект вместо строки-роли; первичный ключ — id, а не путь. Имя — про читаемость,
не про механику.

## 10. Ad-hoc управление транзакциями

**Антипаттерн.** Десятки ручных `commit()`, расставленных по горячему пути, чтобы лечить
конкретные инциденты («commit перед сетевым connect, иначе idle in transaction»).

**Почему больно.** Границы транзакции невидимы и хрупки; забыл один commit — новый инцидент;
каждый инцидент добавляет ещё один ручной commit → снежный ком.

**Как правильно.** Инкапсулируй границы транзакции в контекст-менеджер («короткая транзакция →
commit перед сетевым вызовом → владение клиентом»). Один слой отвечает за when-to-commit.
**Важно:** такие ручные commit часто кодируют **вылеченные инциденты** — не выпиливай их
слепо; переноси семантику в контекст-менеджер и покрывай интеграционным тестом.

## 11. Накопление мёртвого кода

**Антипаттерн.** Неиспользуемые функции/классы (вытесненные новыми), мёртвые импорты,
`__all__` со ссылками на удалённое, закомментированные блоки.

**Почему больно.** Раздувает файлы, путает поиск («какая из двух функций живая?»),
маскирует реальную структуру.

**Как правильно.** Линтер мёртвых импортов (pyflakes/ruff) и мёртвого кода в CI. При удалении
символа грепни его имя по всему проекту И тестам (кроме файла определения) — 0 внешних ссылок
= безопасно. Учитывай re-export (`from mod import name` в другом модуле) и side-effect импорты
(`import models` ради регистрации метаданных ORM — их линтер трогать не должен).

## 12. Рефакторинг без страховочной сети

**Антипаттерн.** Структурные правки без VCS и без известного зелёного состояния тестов
(«отрефакторю, потом проверю»).

**Почему больно.** Нет отката; невозможно отличить «я сломал» от «оно и так падало».

**Как правильно (обязательный чек-лист перед структурным рефакторингом):**
1. **VCS + baseline-коммит.** Нет репозитория — `git init` первым делом.
2. **Зелёный/зафиксированный baseline тестов.** Прогони, запиши список падающих ДО правок —
   это оракул регрессий (сравнивай «новые падения», а не абсолютное число).
3. **Правильное окружение.** Версия рантайма как в проде (Dockerfile/CI), не «что оказалось».
4. **Пофазно.** Маленькие обратимые коммиты; после каждого — регресс-чек (нет новых падений).
5. **Behavior-preserving по умолчанию.** Меняешь структуру — не логику. Изменение поведения —
   отдельно, явно, с флагом-предложением; в проде — с подтверждением владельца.
6. **Проверяй статически то, что тесты не покрывают.** Вынес функцию — pyflakes поймает
   пропущенный захват (undefined name) и лишний (unused). Компиляция ≠ отсутствие NameError.

---

## 13. Не выдумывай бизнес-логику

**Антипаттерн.** Наткнулся на «странность» (статус в одном наборе, но не в другом; поле не
чистится при сбросе) и «починил» по своему разумению.

**Почему больно.** «Странность» может быть намеренной. Слепой фикс в проде ломает
интендед-флоу, о котором ты не знаешь.

**Как правильно.** Если ответа нет в коде-каноне и доках — **не выдумывай**: зафиксируй как
флаг-предложение с точным диффом и спроси владельца. После подтверждения — примени и
задокументируй решение. Отделяй «консолидация без смены поведения» (делай сам) от «фикс
расхождения» (сначала подтверждение).

# Часть II. Антипаттерны БИЗНЕС-логики

Отдельный класс ошибок: код корректен структурно, но **правила предметной области
противоречат друг другу, оставляют сущность в тупике или нарушают заявленный инвариант**.
Их не ловят типы и юнит-тесты — только проход по флоу «а как сущность отсюда выходит?».

## 14. Тупиковые состояния (нет пути self-healing)

**Антипаттерн.** Сущность попадает в статус, из которого **нет автоматического выхода**:
основной цикл перепроверяет только один статус (напр. `pending`), а этот — не в нём; не в
списке «повторяемых»; heal его не трогает. Сущность (и связанные с ней дочерние записи)
выпадает из работы навсегда, до ручной правки БД.
*Пример:* записи в `blocked` / `awaiting_payment` — reconcile проверяет только `pending`,
они не в списке retriable, heal для них нет → зависают вечно вместе с дочерней задачей.
Нарушает принцип «система самовосстанавливается».

**Почему больно.** Тихая деградация: сущности молча копятся в тупике, метрики «работает»,
а часть очереди мертва. Особенно опасно для систем, заявленных как автономные/self-healing.

**Как правильно.** Для **каждого** не-терминального статуса ответь: «кто и по какому условию
вернёт сущность в работу?». Нет ответа — это баг. Веди явную таблицу переходов: статус →
триггер выхода. Терминальные (`completed`/`deleted`) — единственное исключение, и они должны
быть явно помечены терминальными.

## 15. Глобальный флаг для локального намерения

**Антипаттерн.** Действие над ОДНОЙ сущностью включает флаг, влияющий на ВСЕ.
*Пример:* «Выполнить сейчас» на одной задаче вычисляет `ignore_rate_limit =
forced_count > 0` и передаёт его **всему пулу** — в итоге rate-limit обходится у всех
воркеров, а не только у владельца форс-задачи.

**Почему больно.** Ослабляет инвариант (здесь — потолок скорости) для сущностей, не
имеющих отношения к действию. «Ускорить один» превращается в «ускорить всех».

**Как правильно.** Скоупь флаг/исключение к той сущности, которой оно принадлежит
(per-tenant, per-task), а не к глобальному «есть ли хоть один такой». Спроси: «кого именно
это должно затронуть?» — почти никогда не «всех».

## 16. Инвариант, который держится «на надежде» (нет enforcement)

**Антипаттерн.** «Один X — один активный Y» / «в одном ресурсе один владелец» держится только
тем, что «параллельные воркеры вряд ли пересекутся» — без БД-constraint, без блокировки, без
пере-чтения перед записью.
*Примеры:* два параллельных воркера в окне долгого вызова оба видят «активной задачи нет» →
создают две (нет partial unique index на `parent_id` для активных). Или: снимок состояния
ДО `asyncio.gather`, владелец пишется ПОСЛЕ — два владельца одного ресурса.

**Почему больно.** Инвариант нарушается именно под нагрузкой (когда это дороже всего) и
невоспроизводимо в тестах. Документированное «железное правило» по факту не гарантируется.

**Как правильно.** Инвариант уникальности/владения — **структурно**: partial unique index,
`SELECT ... FOR UPDATE`, advisory-lock, или атомарный `UPDATE ... WHERE unclaimed` (claim перед
работой). Снимок состояния до параллельной секции — не источник истины для решения о записи;
перечитывай/клейми внутри критической секции.

## 17. Два правила, противоречащие на границе

**Антипаттерн.** Два независимых правила гейтят одну сущность, и их пересечение отсекает
ровно тот класс, ради которого одно из них введено.
*Пример:* «приоритет = недавно активные, обрабатывать обязательно» (по `last_seen ≤24ч`) vs
возрастной отсекатель «created_at ≤ 3 суток». Старая запись, которая стала активной СЕЙЧАС
(fresh по `last_seen`, но >3 суток по `created_at`), считается приоритетной одним правилом
и выкидывается другим → целевой класс не обрабатывается, хотя это главная цель.

**Почему больно.** Каждое правило по отдельности разумно, а их конъюнкция ломает северную
звезду в углу, который трудно заметить.

**Как правильно.** Когда два условия гейтят одну сущность — проверь их **пересечение** для
класса, который важен каждому правилу. Если правило-приоритет и правило-фильтр расходятся,
явно реши, кто главнее для спорного класса, и задокументируй.

## 18. Read-modify-write через `await`/`commit`-границу

**Антипаттерн.** Между «записал факт A» (commit) и «записал согласованный факт B» есть
`await`/сетевой вызов/второй commit — окно, где состояние рассогласовано, а при падении
между ними остаётся навсегда.
*Пример:* `completed_at` пишется и коммитится сразу (анти-дубль), а `status = completed` —
позже, после пост-обработки; между ними падение → операция выполнена, а родительская
сущность зависла в `in_progress`, и heal на это нет.

**Почему больно.** Редкое, но перманентное рассогласование; «по счастью» защищено от худшего
(двойной отправки), но данные разъезжаются и никто не чинит.

**Как правильно.** Либо один commit на согласованную пару фактов (транзакция), либо явный
reconcile, который ловит «A есть, B нет» и досводит. Инвариант «A ⇒ B» должен кем-то
принудительно восстанавливаться, если между ними есть окно.

## 19. Метрика/флаг посчитаны, но не влияют на решение

**Антипаттерн.** Значение вычисляется (и намекает на намерение «учесть простой пула»), но в
точке решения не используется.
*Пример:* `idle_workers` (простаивающие ready-воркеры) посчитан, но допуск кандидата в буфер
его игнорирует → ready-воркер стоит без работы, хотя задача могла быть поставлена.

**Почему больно.** Создаёт иллюзию, что фактор учтён (он даже назван в коде), а поведение — нет.

**Как правильно.** Если посчитал сигнал — либо примени его в решении, либо удали. Проверь, что
заявленные в правилах исключения («когда пул простаивает…») реально ветвят логику, а не только
присутствуют в тексте правила.

# Часть III. Фронтенд-слоп (React / state / CSS)

Отдельный класс ошибок, что копится, когда UI переписывают под новые флоу.
Типичные симптомы: лента «плывёт», элементы меняют порядок, вёрстка едет на мобиле.

## 20. `Date.now()` как ключ/id элемента списка

**Антипаттерн.** id элемента = `` `item-${Date.now()}` ``, а когда в один тик
добавляли два — костыль `` `item-${Date.now()+1}` ``.

**Почему больно.** Внутри одного тика `Date.now()` совпадает → дубли `key` в
React → перемонтирование, **перескок и дублирование элементов**, потеря стейта.
`+1` не спасает: третий элемент снова коллизит.

**Как правильно.** Монотонный счётчик (`let seq=0; const id=()=>\`m${++seq}\``),
переинициализируемый после rehydrate persist'а (`onRehydrateStorage` → выставить
seq за максимум восстановленных id). Ключ — стабильный доменный id, не время.

---

## 21. Часть ленты рендерится вне массива сообщений (split render state)

**Антипаттерн.** Лента — это `items.map(...)`, но уведомления/баннеры
висят **отдельным блоком над лентой** (`notifications.length > 0 && <div>`), из
другого стора.

**Почему больно.** Порядок в UI больше не отражает порядок событий: блок всегда
сверху, что бы ни случилось после. Два источника истины о том, «что на экране» →
рассинхрон, «прыжки», невозможно вставить сообщение между.

**Как правильно.** **Одна упорядоченная лента** с типизированными элементами
(`kind: 'text' | 'card' | 'notice' | 'system'`). Всё, что видит юзер, —
элемент `items`. Ничего не рендерится «сбоку».

---

## 22. Презентационный HTML/разметка в модели данных

**Антипаттерн.** В стор кладётся строка с `` `<img src=...>` `` и `**bold**`,
потом выводится через `dangerouslySetInnerHTML`. Функция `entityToHtml()`
собирает сущность в один HTML-blob и хранит его как `content` сообщения.

**Почему больно.** XSS-поверхность; смена языка/вёрстки требует перегенерации
сохранённого текста; нельзя переиспользовать данные (та же сущность в модалке —
другой layout); persist хранит вёрстку, а не факты.

**Как правильно.** В модели — **только данные** (`{kind:'card', entityId}`).
Рендер — React-компонент (`<EntityView>`), переиспользуемый и в ленте, и в
модалке. `**bold**` → безопасный парсер в `<strong>`, без `dangerouslySetInnerHTML`.

---

## 23. Фиксированные `vh` и `overflow:hidden` на body вместо flex-каркаса

**Антипаттерн.** `body{overflow:hidden}`, `.scroll-area{max-height:50vh;min-height:40vh}`,
высоты в `vh`.

**Почему больно.** `100vh` на мобиле не учитывает адресную строку → контент под
экраном/обрезан. Жёсткие `vh` на внутренних блоках дерутся между собой. Скролл
ломается, когда клавиатура выезжает.

**Как правильно.** Каркас: `h-[100dvh]` (dynamic viewport) на корне, `flex-col`,
скролл-регион = `flex-1 min-h-0 overflow-y-auto`. Высоты не хардкодим — их задаёт
flex. `viewport-fit=cover` + safe-area при необходимости.

---

## 24. Забытый `min-width:0` на flex-детях → горизонтальный «разъезд»

**Антипаттерн.** `flex-1` textarea и скролл-лента без `min-w-0`; на мобиле весь
макет уезжает вправо и обрезается.

**Почему больно.** У flex-элемента `min-width:auto` по умолчанию: он не даёт
себя сжать меньше контента (длинное слово, `<textarea>`), и колонка распирается
шире вьюпорта. Дефект невидим на десктопе, вылезает на 390px.

**Почему коварно диагностируется.** Headless-скриншот с `--window-size=390` врёт
(рендерит контент шире окна). Мерить надо реальный вьюпорт: CDP
`Emulation.setDeviceMetricsOverride` + сравнить `documentElement.scrollWidth` с
`innerWidth` и собрать элементы с `getBoundingClientRect().right > innerWidth`.

**Как правильно.** На каждого flex-ребёнка, который должен сжиматься, — `min-w-0`
(и `min-h-0` для вертикали). Проверка: `scrollWidth === innerWidth` на 390px.

---

## 25. Дублирование токенов дизайна и «god-комponent» вьюхи

**Антипаттерн.** Палитра/шрифты объявлены и в `global.css` (`:root`), и повторно
в корневом компоненте; один экранный компонент на 200+ строк держит хедер, ленту, ввод,
парсинг маркеров, модалку и инлайн-стили; каждая кнопка стилизована заново.

**Почему больно.** Меняешь цвет — правишь в N местах, они расходятся.
Компонент невозможно переиспользовать/тестировать по частям. Инлайн-`style` мимо
токенов.

**Как правильно.** **Один** источник токенов (CSS variables, `@theme` в Tailwind,
design tokens). Мелкие переиспользуемые примитивы
(`Button`, `Chip`, `Modal`, `CardView`) — стиль объявлен один раз. Вьюха —
композиция мелких компонентов (`Screen` = `Header`+`List`+`Composer`),
каждый со своей ответственностью (см. §3).

---

## 26. Несколько boolean-флагов на одну ось состояния

**Антипаттерн.** Одно решение («сущность вне пула», «низкий приоритет», «тип защиты»)
закодировано 2–4 полями, которые почти всегда выставляются вместе или дублируют уже
существующий tier/enum. Фильтры в SQL копируют `flag_a AND NOT flag_b OR flag_c`.

**Почему больно.** Новый код забывает один из флагов → дыра (сущность попала / не попала).
Heal-логика чинит одну комбинацию, другая висит вечно. UI читает флаг A, worker — B.

**Как правильно.**
- **Одна ось — один канонический признак** для допуска/исключения; подтип — отдельное
  поле только если нужен другой heal/UI, с инвариантом записи «подтип ⇒ канонический».
- **Не дублировать то, что уже в tier/enum** — не второй boolean на ту же семантику.
- **Единая точка чтения и записи**; grep по старым полям в фильтрах — красный флаг.
- Legacy-строки — одноразовый heal в reconcile, не вечная проверка OR в hot-path.

*Иллюстрация:* допуск в пул читается через один `excluded`; подтип «сильная защита» —
отдельное поле для heal/UI с инвариантом `strong ⇒ excluded`. Второй boolean для того же
tier удалить.

## 27. Два пула решают одну задачу приоритизации

**Антипаттерн.** Пул отбора (сырьё) и пул обработки (готовые задачи) каждый вводит **свою**
сортировку/веса — неясно, какой порядок канонический.

**Почему больно.** Элемент #1 в UI отбора может обработаться позже «худшего» из очереди.
Правила приоритета правят в двух местах; одно забывают — расхождение.

**Как правильно.**
- **Один канонический порядок** — пул отбора (`ORDER BY` / score).
- Пул обработки: срочный флаг (force) + **тот же** порядок по сущности; без второго tier/score.
- Поправки приоритета — только в отборе, не дублировать в обработке.

*Иллюстрация:* `process_queue_order` = `urgent_flag` + тот же `selection_order`, что у пула отбора.

---

## 28. Два поля «не публиковать раньше T»

**Антипаттерн.** CD после успеха (`comment_publish_next_at`) и «пауза» после ошибки/оператора
(`publish_paused_until`) — два столбца на одну ось «earliest publish time». `account_can_publish_now`
проверяет оба; писатели забывают один.

**Почему больно.** Расхождение UI и worker; heal одного поля не чинит другой; blocking-badge
считает только одно.

**Как правильно.**
- Одно поле + `defer_until(account, t)` = `max(current, t)`; читатели только его.
- Legacy-столбец — merge в init/migrate, не вечный OR в hot-path.

*Иллюстрация:* `account_publish_not_before()` + `defer_account_publish_until()`.

---

## 29. Force / bypass поверх очереди и антибана

**Антипаттерн.** Кнопка «сейчас» или флаг на сущности обходит CD, ratio, глобальный ORDER BY;
отдельные `bypass_account_ids` в publish tick.

**Почему больно.** Дублирует приоритет; ломает антибан; in-flight guard обрастает исключениями.

**Как правильно.**
- Один канонический порядок очереди; аккаунт — исполнитель, не владелец сортировки.
- Ops-сброс паузы аккаунта — отдельно, без обхода SpamBot/quarantine.

*Иллюстрация:* удалён `publish_requested_at`; `fetch_global_publish_queue` + фильтр по аккаунту.

# Часть IV. Конкурентность, кэш и ресурсы

Класс ошибок, который вылезает только под нагрузкой в долгоживущем воркере: локи не покрывают
то, что должны; кэши растут и опережают БД; ретраи синхронизируются в «стадо». Их не ловят
юнит-тесты — только модель «что происходит, когда два пути идут одновременно / процесс живёт неделю».

## 30. Разные локи на один и тот же ресурс (split-lock granularity)

**Антипаттерн.** Один ресурс (аккаунт, соединение, файл) защищён **двумя разными** локами под
разные «концерны» — `operation_lock` для длинных операций и `connect_lock` для connect/disconnect,
— а вызывающие берут **разные подмножества**. Один путь держит только op-lock и работает с живым
клиентом; другой путь берёт только connect-lock и делает disconnect — не пересекаясь по локу.
*Пример:* операция под `account_telegram_operation` (op-lock) идёт в сети; параллельный
recycle/connect берёт `account_telegram_exclusive` (connect-lock), видит его свободным и
дисконнектит клиента из-под работающей операции. Инвариант «операции на аккаунте сериализованы»
держится для op-vs-op и **молча не держится** для op-vs-connect.

**Почему больно.** Взаимное исключение существует «на бумаге» (два лока названы, оба про аккаунт),
но критические секции не пересекаются, поэтому гонка возможна именно там, где её не ждут. Отличается
от §16: там нет enforcement уникальности в БД, здесь enforcement есть, но **гранулярность лока не
покрывает весь жизненный цикл ресурса**.

**Как правильно.** Один лок на ресурс на **всё время владения** (connect + операции + disconnect —
одна критическая секция), либо путь disconnect обязан брать тот же лок, что и операция. Правило:
«кто трогает ресурс — берёт один и тот же лок»; два лока на один ресурс под разные глаголы — красный
флаг. Проверь матрицу: для каждой пары путей (A держит лок X, B держит лок Y) — могут ли A и B
идти одновременно, и безопасно ли это.

---

## 31. In-memory кэш без активного вытеснения (lazy-only expiry → безграничный рост)

**Антипаттерн.** Модульный `dict`-кэш с TTL, где срок жизни проверяется **только при повторном
чтении того же ключа** (`if entry.expires_at > now`). Нет ни фонового свипа, ни лимита размера.
Ключ включает монотонно растущее множество (id поста/сообщения, id сущности) → каждый когда-либо
виденный элемент оставляет запись навсегда.
*Пример:* кэш доступности с ключом `channel:message_id` — на каждый просканированный пост новая
запись; `invalidate_channel` чистит только явно инвалидированный канал. Так же растут словари
локов по `account_id`.

**Почему больно.** Тихая утечка памяти в процессе, который живёт неделями: метрики «работает»,
пока RSS ползёт вверх до OOM. Ленивый expiry вводит в заблуждение («TTL же есть») — но истёкшие
записи не удаляются, если ключ больше не запрашивают.

**Как правильно.** Ограничь кэш **по размеру** (LRU/`OrderedDict` с потолком, `lru_cache`), особенно
если пространство ключей неограничено. Плюс периодический свип (в уже существующем maintenance-тике)
`del keys where expires_at <= now`. TTL без вытеснения по размеру для растущего keyspace — не кэш, а
утечка.

---

## 32. Backoff скопирован с расхождениями и без jitter (thundering herd)

**Антипаттерн.** Ретрай-петли в N местах, каждая со своей ручной формулой линейного/экспоненциального
backoff, разными константами и **разной базой индекса** (`0.25*(attempt+1)` тут, `0.2*attempt` там —
уже разошлись), и **нулевым jitter** везде.
*Пример:* 6 сайтов ретрая с `sleep(min(2.0, 0.25*(attempt+1)))` / `sleep(0.5*(attempt+1))` /
`sleep(min(2.0, 0.2*attempt))` — часть на `attempt+1`, часть на голом `attempt`.

**Почему больно.** Это §4 (копипаст), но с доменным жалом: когда весь пул упирается в один и тот же
FloodWait или локнутую БД, все воркеры ретраят по **синхронному** расписанию → «стадо» бьёт по тому
же ресурсу разом, усугубляя затор, который пытались переждать. Расхождение базы индекса делает
поведение непредсказуемым от сайта к сайту.

**Как правильно.** Один хелпер `retry_backoff(attempt, *, base, cap, jitter=True)` (или декоратор /
async-контекст), используемый всеми сайтами. Обязателен **рандомизированный jitter**
(`base * factor * (1 + random.uniform(...))`), чтобы пуловые ретраи декоррелировали. Классификацию
retriable-vs-fatal — по типу исключения внутри хелпера (см. §7), а не по подстроке на каждом сайте.

---

## 33. Write-through кэш обновляется ДО commit (кэш опережает источник истины)

**Антипаттерн.** Модульный/процессный кэш состояния присваивается новым значением **до** `flush`/
`commit`, а запись в БД идёт после (и транзакция коммитится ещё позже вызывающим).
*Пример:* `_state_cache = dict(state)` на строке выше, `session.flush()` — ниже; при исключении на
flush или откате внешней транзакции в кэше остаётся состояние, **которого нет в БД**, и следующий
`load(fresh=False)` отдаёт фантом в логику принятия решений (тюнинг пейсинга AIMD).

**Почему больно.** Зеркало §18, но в сторону кэша: кэш **ведёт** БД вместо того, чтобы следовать за
ней. Рассогласование редкое (только при сбое между присваиванием и коммитом), но перманентное на
время жизни процесса, и влияет на решения.

**Как правильно.** Обновляй write-through кэш **только после** durably-commit (заполняй кэш там же,
где коммитишь, или при следующем `load(fresh=True)`). Ещё лучше — вообще не write-through: пусть кэш
populate-ится только из подтверждённых чтений. Кэш всегда **следует** за источником истины, никогда
не опережает.

---

## 34. Heal чинит только один из парных фактов (ложная уверенность в покрытии окна)

**Антипаттерн.** Есть окно между commit факта A и commit согласованного факта B (§18), и под него
**есть** специальный reconcile/heal — но он досводит **только A** (или только статус), забывая
парные побочные записи, которые тоже пишутся во второй фазе.
*Пример:* при краше между «черновик отправлен» (commit A) и «пост=PUBLISHED + пейсинг аккаунта»
(commit B) heal переводит пост в PUBLISHED, но **не** проставляет `publish_next_at` (антиспам-CD),
`last_published_at`, `success_count` — аккаунт публикует back-to-back на следующем тике, нарушая
инвариант «без back-to-back».

**Почему больно.** Хуже, чем отсутствие heal: heal **создаёт ложную уверенность**, что окно покрыто
(«же есть reconcile»), при этом чинит одну половину и оставляет другую рассогласованной. Ревьюер
видит heal и считает инвариант защищённым.

**Как правильно.** Heal обязан восстанавливать **все** факты второй фазы, а не только главный статус.
Перечисли явно, что пишется во второй фазе (статус + счётчики + тайминги + скоуп-поля), и убедись,
что reconcile досводит **каждое**. Тест: «крашни между commit A и B → прогони heal → проверь, что
состояние идентично успешному проходу», а не только что статус верный.

---

## 35. Лимит проверяется как булев гейт, а не как счётчик-потолок (под fan-out)

**Антипаттерн.** Глобальная квота (N в день на всех) снимается **одним снимком** до параллельного
`gather`, передаётся каждому исполнителю, а гейт проверяет только **наличие** остатка, не
per-исполнитель потолок. Декремент счётчика — **после** действия и только записывает, никогда не
блокирует.
*Пример:* `slots = limit - used` (снимок), передан всем; гейт `if slots <= 0: return False`; при
`slots=2` и 3 готовых кандидатах все трое проходят `2 <= 0 → False` и стартуют разом — глобальный
лимит пробит каждый тик. Лок вокруг декремента защищает счётчик, но не гейтит действие.

**Почему больно.** TOCTOU на квоте: «осталось 2» истинно для всех троих одновременно. Булев гейт
(«есть ли хоть слот») ≠ атомарный расход слота. Родственно §16, но ось — **счётчик/квота**, а не
уникальность владения.

**Как правильно.** Расходуй слот **атомарно перед** действием (claim: `UPDATE ... SET used=used+1
WHERE used < limit RETURNING`, или захват слота под локом до старта, а не запись факта после).
Действие стартует, только если слот реально захвачен. Снимок «сколько осталось» до fan-out — не
основание для решения внутри параллельной секции; клейми внутри неё.

---

## 36. Enforcement инварианта зависит от бэкенда/диалекта

**Антипаттерн.** «Железное правило» (уникальность, владение) enforced структурно **только на одном
бэкенде**: race-closing перечитка спрятана за `if dialect == "postgresql"` (advisory-lock + re-read),
а на любом другом бинде решение принимается по устаревшему in-memory снимку.
*Пример:* «один канал → один аккаунт»: на PostgreSQL — `pg_advisory_xact_lock` + свежий
`reserved_by_other`; на прочих БД — только pre-gather снимок карты резерваций → два тика читают
`owner=None` и оба публикуют.

**Почему больно.** Инвариант документирован как безусловный, но его **enforcement** условен. Тесты
на SQLite «зелёные» (guard не срабатывает), прод на Postgres защищён, а стейджинг/иной бэкенд — дыра.
Расходится не инвариант, а гарантия его соблюдения — что заметить труднее.

**Как правильно.** Enforcement инварианта должен быть **бэкенд-независимым** или явно закрывать
незащищённые бэкенды. Если структурная защита есть только на одном диалекте — либо продублируй
эквивалент (claim через атомарный `UPDATE ... WHERE unclaimed`, работающий везде), либо запрети
незащищённый бэкенд в проде явной проверкой на старте, а не молчаливым `if dialect == ...`.

---

## 37. Одно событие инкрементит счётчик на двух путях (double-count → преждевременный терминал)

**Антипаттерн.** Один провал/успех проходит через **две** ветки обработки в рамках одной попытки, и
**каждая** бампает один и тот же счётчик-стрик. Порог эскалации достигается вдвое быстрее заявленного.
*Пример:* провал bypass'а: сначала прямой `mark_weakly_protected(bypassed=False)` (стрик +1), затем
классификатор возвращает `"weak_failed"` для того же события и `apply_outcome` снова зовёт
`mark_weakly_protected(bypassed=False)` (стрик +1 ещё раз) → порог «5 провалов → перманентная сильная
защита» срабатывает после ~2–3 реальных провалов; канал бросается зря, черновики удаляются.

**Почему больно.** Терминальная/необратимая эскалация (удаление из очереди, удаление данных) на основе
завышенного счётчика. Каждая ветка по отдельности «разумна» — баг в том, что обе бьют по одному
счётчику на одном событии.

**Как правильно.** Инкремент счётчика-эффекта — в **одной** точке на событие. Если событие проходит
через несколько веток (прямой марк + классификатор-outcome), реши, кто владелец инкремента, и убери
дубль. Идемпотентность по попытке: «этот attempt уже учтён» (dedup-ключ), чтобы повторный путь не
досчитывал. Для терминальных порогов особенно — проверь, что один провал = ровно +1.

# Часть V. API / HTTP-слой

Класс ошибок, который копится в слое обработчиков, когда эндпоинты пишут по одному под каждый
экран. Симптомы: один запрос кладёт процесс; клиент видит «тот же» объект по-разному; забытый
`_require_auth` открывает эндпоинт наружу.

## 38. Недоверенный ввод → рефлексия (`getattr(Model, param)`) без allow-list

**Антипаттерн.** Имя поля/сортировки из query-параметра прокидывается прямо в
`getattr(Model, sort_by, default)` / `order_by` без белого списка.
*Пример:* `sort_column = getattr(NegativePost, sort_by, NegativePost.post_date)` — клиент сортирует
по любой колонке (тяжёлое поле → full-scan) или по не-колонке (`sort_by=__class__` → 500). Рядом
в том же файле соседний эндпоинт уже делает правильно — через `sort_columns`-словарь.

**Почему больно.** Атрибут-инъекция: недоверенная строка выбирает атрибут кода. DoS дорогой
сортировкой + 500 с трейсбеком наружу. Правильный паттерн часто уже есть рядом и обойдён.

**Как правильно.** Только **явный allow-list** `{"post_date": Model.post_date, ...}`; неизвестный
ключ → дефолт или 400. Ноль `getattr(Model, <user input>)`. То же для любого «имя из запроса →
атрибут/метод/файл».

---

## 39. Мутирующий эндпоинт без идемпотентности («set», который на деле toggle)

**Антипаттерн.** Хендлер называется «установить роль/флаг», а внутри инвертирует текущее значение
(`account.is_monitoring = not account.is_monitoring`), либо мутация не защищена от повторной
доставки. Повтор запроса (двойной клик, ретрай сети) меняет результат.
*Пример:* `POST .../role` с телом `role: "monitoring"` флипает поле — второй такой же запрос
возвращает всё назад, ровно наоборот к намерению.

**Почему больно.** Ретраи и дабл-сабмиты — норма в вебе; неидемпотентная мутация тихо
инвертирует состояние, от которого зависит гейт публикации. «Отправил дважды» ≠ «сделал дважды».

**Как правильно.** Мутация выражает **целевое состояние**, а не дельту: `is_monitoring =
(role == "monitoring")` или явный `enabled: bool`. Небезопасные повторы защищай ключом
идемпотентности; семантика глагола («set») должна совпадать с поведением.

---

## 40. Безлимитная выборка на export/aggregate (есть пагинация — но не здесь)

**Антипаттерн.** Списочный эндпоинт пагинируется, а «выгрузка всего» / отчёт грузит **все**
совпавшие строки в память (`.scalars().all()` без `.limit()`), затем материализует xlsx/CSV.
*Пример:* `/api/posts` с `LIMIT/OFFSET`, а `/api/posts/export` — `rows = (await
db.execute(q)).scalars().all()` по всей таблице.

**Почему больно.** Неограниченный рост памяти и времени: по мере роста таблицы один запрос
исчерпывает процесс (OOM/timeout). Отличается от §31 (in-memory кэш) — здесь **разовая** выборка
из БД без потолка.

**Как правильно.** Жёсткий потолок строк (например 50k) с явной ошибкой при превышении, либо
стриминг/чанки (cursor-пагинация). Любая выборка, чей размер задаёт пользователь/данные, — с
верхней границей.

---

## 41. Сырой текст исключения в ответе наружу

**Антипаттерн.** `raise HTTPException(502, f"...: {e}")` / `{"error": str(e)}` — текст исключения
Telethon/SQLAlchemy уходит клиенту.

**Почему больно.** Утечка внутренностей (драйвер, фрагменты SQL, пути); клиент привязывается к
изменчивому тексту ошибки. Отличается от §7: §7 — про **классификацию** по подстроке, здесь — про
**эмиссию** сырого текста наружу.

**Как правильно.** Полную ошибку — в лог на сервере; наружу — стабильное generic-сообщение +
код ошибки. Никогда `str(e)` в теле ответа/в UI.

---

## 42. N+1 в эндпоинте при наличии готового batch-хелпера

**Антипаттерн.** Хендлер в цикле по N сущностям делает по запросу на каждую, хотя batch-версия
**уже написана и используется** горячим путём.
*Пример:* `for acc in pool: published_today_by_id[acc.id] = await published_today_count(...)` —
при том что `published_today_counts_by_account_ids` (один `GROUP BY`) существует и вызывается
воркером.

**Почему больно.** Латентность растёт линейно с пулом на часто-опрашиваемом дашборд-эндпоинте.
Это §1/§5 (каноническая функция обойдена), помноженное на классический N+1.

**Как правильно.** Один агрегатный запрос (`GROUP BY ... WHERE id IN (...)`). Цикл `await`-запросов
по коллекции — красный флаг; ищи/выноси batch-хелпер и зови его из **обоих** мест.

---

## 43. Сквозной инвариант (auth) — построчным вызовом, а не структурно

**Антипаттерн.** `_require_auth(request)` скопирован в каждый хендлер (десятки раз) вместо
middleware / router-level `dependencies=[Depends(...)]`. Новый эндпоинт, забывший строку, — молча
публичный.

**Почему больно.** Безопасность держится на дисциплине, ровно как §16 «на надежде»: инвариант
«каждый `/api/*` защищён» не enforced структурно; забытый вызов не ловится ни типами, ни тестами.

**Как правильно.** Сквозной концерн (authn/authz, тенант, аудит-лог) — на уровне
router/middleware (`APIRouter(dependencies=[Depends(require_auth)])`), чтобы обойти было **нельзя**;
исключения (`/healthz`, `/login`) — явным opt-out, а не opt-in на каждый защищённый.

---

## 44. Один энтити — N разошедшихся сериализаторов (разный DTO на каждом маршруте)

**Антипаттерн.** Одна модель превращается в dict в ≥5 местах (инлайн в каждом эндпоинте), и наборы
полей/округления разошлись: один маршрут отдаёт `forwards`, другой `embedding_category`, третий —
своё подмножество того же поста.

**Почему больно.** Клиент видит «тот же» объект с разными полями/точностью в зависимости от роута;
добавить поле = править N мест (уже разошлись). Facet §4, но со специфическим жалом «одна сущность —
N wire-форм».

**Как правильно.** Один билдер `serialize_post(post, *, variant=...)`, вызываемый отовсюду; варианты
маршрута — параметр, а не копипаст inline-словаря.

# Часть VI. Async-исполнение, ресурсы и устойчивость (продолжение)

Продолжение §30–37: ещё класс дефектов долгоживущего async-воркера — блокировка петли, утечки на
error-пути, кэш с неверным ключом, отсутствующий предохранитель, недостижимые ветки.

## 45. Синхронный/блокирующий I/O (и `threading.Lock`) на event-loop

**Антипаттерн.** В async-пути — блокирующий `open()/read()/write()`, `path.read_bytes()`,
`requests`, или модульный `threading.Lock` вокруг файла. Часто рядом тот же проект **умеет**
правильно (`asyncio.to_thread`/`run_blocking_io`) — но конкретный путь зовёт блокирующе.
*Примеры:* хранилище фидбэка читает до 5000 строк файла синхронно прямо из async-хендлера под
`threading.Lock`; sidecar-JSON креденшелов читается `path.read_bytes()` в горячем connect-пути,
хотя копия сессии рядом уже идёт через `read_bytes_async`.

**Почему больно.** Блокирующий вызов останавливает **весь** event-loop: под нагрузкой каждый запрос
встаёт, линейное чтение файла масштабируется на loop-треде. `threading.Lock` в async — застывшая
петля вместо честной сериализации.

**Как правильно.** Любой блокирующий I/O в async — через `asyncio.to_thread`/`run_in_threadpool`
(или в БД). Для взаимного исключения в async — `asyncio.Lock`, не `threading.Lock`. Проверь: путь
делает то же, что уже делает правильный сосед?

---

## 46. Утечка ресурса на error-пути (partial-init без cleanup при исключении)

**Антипаттерн.** Между «захватил ресурс» (`connect()`) и «вернул наружу» есть шаг, который может
бросить (`get_me()` под таймаутом), и он **не** обёрнут в cleanup. Часть веток чистят
(`is_authorized` → `disconnect()` → raise), а следующая по коду — нет.
*Пример:* `create_telegram_client`: ветка не-авторизации дисконнектит перед `raise`, а `get_me` под
30s-таймаутом — нет; при его падении живой клиент (сокет + прокси + SQLite-хендл) утекает, потому
что вызывающему уходит только исключение. Под connect-retry — по клиенту на каждую неудачу.

**Почему больно.** Медленная утечка сокетов/хендлов ровно на пути, который повторяется под ретраем;
воспроизводится только при сбое. §31 — про рост кэша, здесь — про **не освобождённый на исключении**
захваченный ресурс.

**Как правильно.** Всё между acquire и успешным `return` — под `try/except: <release>; raise` (или
`async with`/контекст-менеджер, владеющий жизненным циклом, — см. §10). Правило: если функция
захватывает ресурс и может бросить до отдачи наружу — она обязана его закрыть на error-пути.

---

## 47. Shared-кэш с неверной гранулярностью ключа → утечка данных между identity

**Антипаттерн.** Процессный кэш ключуется по «имени» без учёта identity сессии/аккаунта/тенанта, а
хранит значение, **валидное только в рамках этой identity**.
*Пример:* глобальный entity-cache по `username` хранит Telegram-`entity` с `access_hash`, который
**per-session**; сущность, разрезолвленная под аккаунтом A, отдаётся клиенту аккаунта B → на его
сессии `access_hash` невалиден → `PeerIdInvalidError`. Симптом «лечат» разбросанным
`invalidate + retry` — костыль поверх неверного ключа.

**Почему больно.** Тихая порча корректности (не рост памяти — это §31 на той же структуре). Данные
одного контекста утекают в другой; баг всплывает только при >1 identity и объясняет «магические»
инвалидации-ретраи вокруг.

**Как правильно.** Ключ кэша включает **всю** identity, от которой зависит значение:
`(account_id/session, username)`. Либо кэшируй только identity-независимую часть (username→id) и
пере-резолви per-client то, что привязано к сессии.

---

## 48. Нет защитного clamp на safety-critical константе (рассинхрон с соседями)

**Антипаттерн.** Самая рискованная тайминг/лимит-константа — единственная **без** нижнего clamp,
хотя все соседние хелперы защитно клампят (`max(5.0, …)`, `max(2, …)`). При значении `0`
предохранитель молча отключается.
*Пример:* антиспам-интервал публикации: `interval_min=interval_max=0 → return 0`, и планировщик
тогда **не ставит** deferral вовсе → back-to-back публикация — ровно то, что запрещено. При этом
`telethon_timeout`/`circuit_breaker`/`quarantine` рядом свои полы клампят.

**Почему больно.** Одна опечатка в конфиге/легаси-путь импорта тихо снимает самый ban-релевантный
предохранитель — без ошибки и лога. Непоследовательность клампов делает «безопасное» значение
опасным именно там, где цена выше всего.

**Как правильно.** Safety-critical константу клампь **жёстким минимумом** у источника
(`max(MIN_PUBLISH_INTERVAL, …)`), консистентно с соседями; предохранитель нельзя полностью выключить
конфигом. Значение `0`/`disabled` для защиты — только через явный, залогированный, отдельный флаг.

## 49. Два предиката на одну колонку противоречат → ветка недостижима (мёртвый self-heal)

**Антипаттерн.** В одном запросе/условии два предиката на **одну колонку**, где один строго сильнее
другого, и более сильный делает спроектированную ветвь слабого **недостижимой**. Обычно так умирает
задуманный self-heal.
*Пример:* `active_publish_in_flight_sql_filter` разрешает «stale in-flight > 20 мин» (reclaim), но
рядом стоит `publish_error IS NULL`, а in-flight-маркер пишется **в** `publish_error` → строка
in-flight никогда не проходит второй предикат → 20-минутный reclaim мёртв; фактическое
восстановление — только удаление по TTL через 24 ч. Хелпер `is_stale_publish_in_flight` — 0 вызовов.

**Почему больно.** Хуже, чем отсутствие heal (ср. §34): механизм **выглядит** живым (хелпер,
константа TTL, SQL-ветка), ревьюер считает окно покрытым, а ветка не срабатывает никогда —
восстановление тихо деградировало с 20 мин до 24 ч.

**Как правильно.** Для колонки, перегруженной двумя смыслами (маркер in-flight vs записанная
ошибка), — **разведи** их (отдельная `send_claimed_at` вместо перегрузки `publish_error`), чтобы
предикаты не гасили друг друга. Проверяй достижимость каждой спроектированной ветви: «при каких
данных этот OR/branch реально выполняется?»; хелпер с 0 вызовов — либо подключить, либо удалить.

## 50. Бейдж UI из произвольного текста БД или regex на клиенте

**Антипаттерн.** Статус/бейдж для оператора собирается из **свободного текста** в колонке
(`problematic_reason`, `last_error`) через regex на фронте или heal в SQL (`ILIKE '%маркер%'`), либо
из **нескольких boolean** на одну ось (§26). Альтернатива: enum есть, но **UI-словарь живёт только
на одном маршруте API** — остальные отдают «сырой» статус, фронт после рефактора рисует пусто (§44).

**Почему больно.** Heal перезаписывает текст → бейдж и подпись расходятся (бейдж «Сильно защищён»,
текст «админы удаляют»). Regex хрупок к формулировкам. Частичный перенос UI на сервер без единого
`serialize_*` — регрессия: в одной вкладке бейдж есть, в другой «—».

**Как правильно.**
- **Одна ось — enum/колонка состояния** (`protection_kind`, `comment_generation_status`); тексты
  бейджа — **серверный словарь** (`*_ui_payload`), не парсинг reason.
- Свободный текст в БД — только detail/tooltip для оператора, **не** классификация бейджа.
- Один билдер полей UI на сущность; **все** wire-формы поста/канала/черновика вызывают его (§44).
- После выпила client-side map — grep: нет маршрута, где фронт ждёт `*_badge_label`, а API не отдаёт.

*Иллюстрация:* `protection_kind` + `channel_protection_ui_payload()`; посты —
`serialize_post()` / `post_comment_ui_payload` во всех `/api/posts*`; комментарии —
`serialize_comment()` / `comment_ui_payload` во всех `/api/comments*`; legacy regex и transitional aliases удалены.

## 51. «Последняя запись на группу» — full scan + dedupe в Python

**Антипаттерн.** Для «последний scan/лог/событие на канал» — `SELECT * FROM logs WHERE group_id IN (…)
ORDER BY group_id, ts DESC`, затем в Python «первый на группу, которого ещё нет в dict». На prod при
тысячах строк на группу — сотни ms ORM + память, хотя нужно ≤N строк (по одной на группу).

**Почему больно.** Латентность растёт с историей, не с числом групп; индекс по `group_id` без `(group_id,
ts DESC)` не спасает от чтения всей истории. Симптом: «список каналов» 800 ms при 80 каналах.

**Как правильно.**
- `ROW_NUMBER() OVER (PARTITION BY group_id ORDER BY ts DESC)` + `WHERE rn <= K` (K с запасом, если
  верхние строки фильтруются в коде — proxy-transient и т.п.).
- Индекс `(group_id, ts DESC)` под window/partition.
- Чистая функция `pick_latest_*` — только для unit-теста фильтра поверх уже ограниченного набора.

*Иллюстрация:* `load_last_scan_by_channel_id` — top-5 per channel в SQL, не 32k `scan_logs`.

## 53. Градиентный текст (`background-clip:text` + прозрачная заливка)

**Антипаттерн.** Заголовок/лого залиты `linear-gradient` через
`-webkit-background-clip: text; -webkit-text-fill-color: transparent`. Часто ещё и
с `drop-shadow`-фильтром вместо `text-shadow`, потому что текст «невидимый».

**Почему больно.** Контраст неконтролируем (низ градиента сливается с фоном →
плохая читаемость и провал по WCAG). Прозрачная заливка ломает выделение и
подсветку поиска, а в canvas/`measureText` вообще недоступна. При смене шрифта или
переносе строки градиент «съезжает». В 9 из 10 случаев это чисто декоративный слой,
который читается как шаблонный AI-slop, а не как осмысленный акцент.

**Как правильно.** Текст — **сплошным цветом** из токенов; глубину/эмбоссинг дают
`text-shadow` (жёсткая тёмная кромка + мягкое свечение), а не заливка градиентом.
Градиенты — для **реальных поверхностей и иллюстраций** (кнопка, панель, фон,
canvas-арт), не для глифов. Нужен «металлический» текст — делай его артом (SVG/canvas
со своей геометрией), а не хаком заливки.

*Иллюстрация:* лого и `.result-title` в Pardon переведены со `background-clip:text`
на `color: var(--gold)` + `text-shadow`; `ctx.createLinearGradient` в `render.js`
остались — они красят дерево/стекло/металл, а не текст.

## 54. Хардкод отступов/ширин мимо шкалы; контролы «слипаются»

**Антипаттерн.** Ширины (`min(360px,86vw)` тут, `min(380px,88vw)` там), гэпы
(`gap:8px` / `10px` / `12px`), радиусы и брейкпоинты рассыпаны инлайном по правилам
компонентов. Вертикального ритма нет — кнопки/поля идут впритык, **«слипаются»**.
(Частный случай §25: «единый источник токенов» — это не только палитра/шрифты, но и
**ширины, отступы, радиусы, брейки**.)

**Почему больно.** Одинаковые сущности расходятся по значению (колонка 360 против 380);
правка «сделать пошире / добавить воздуха» — grep по N местам, часть забывают → разнобой.
На мобиле ритм плывёт. Экран выглядит как набор случайных чисел, а не как система;
контролы без зазора читаются как «слипшиеся», в них тяжелее попасть пальцем.

**Как правильно.** Одна **шкала интервалов** и семантические токены в `:root`
(`--control-w`, `--stack-gap`, `--overlay-gap`, `--row-gap`, `--list-gap`, `--radius`);
компоненты ссылаются на токен, не на число. Между стопкой интерактивных контролов —
всегда `--stack-gap` (кнопки не впритык). Ширина колонки — один responsive-токен
(`min(px, vw)`), не голый `px` (см. §23). *Проверка:* grep по `px` в `gap:`/`width:`
вне `:root` — красный флаг; одинаковые сущности — один и тот же токен.

*Иллюстрация:* в Pardon все ширины сведены к `--control-w`, отступы — к
`--stack-gap`/`--overlay-gap`/`--row-gap`/`--list-gap`; лобби-меню получило `--stack-gap`
между рядами — кнопки перестали слипаться.

## 55. Клиент отдаётся сырым деревом исходников; «обфускация как безопасность»

**Антипаттерн.** Браузер грузит клиент как есть — дерево ES-модулей (`/client/main.js`,
`/engine/*`) раздаётся статикой один-в-один с диска: исходники, комментарии, структура
видны в DevTools. Зеркальный перекос: обфускацию/минификацию вешают как **«защиту»** и
кладут в клиент секрет/проверку прав в расчёте, что их «не найдут».

**Почему больно.** Два разных вреда. (1) Без сборки клиент — это публичный read-only
исходник: вся структура, имена и комментарии наружу, плюс лишний вес и запросы (нет
bundle/minify). (2) Обфускация **≠** безопасность: клиент всегда исполним и читаем
(deobfuscate, breakpoint, network-tap), поэтому любой секрет или проверка доступа,
живущие в клиенте, — уже дыра. «Защита через непонятность» держится на надежде (см.
главный принцип: инвариант на дисциплине не держится).

**Как правильно.** Клиент **собирается** (bundle + minify, опц. obfuscate) в артефакт; в
прод раздаётся **только** собранный бандл, дерево исходников (`/engine`, `/client`) не
монтируется. Минификация/обфускация — чтобы поднять порог входа и срезать вес, **не** как
граница безопасности. Граница — сервер: он авторитетен (клиент шлёт только ввод), никаких
секретов/ACL в бандле; source maps — только в dev. *Проверка:* в прод-раздаче нет ни
одного `.js` из `src`-дерева с комментариями; ничего в клиенте, что нельзя показать юзеру.

*Иллюстрация:* Pardon в prod отдаёт один минифицированный бандл вместо монтирования
`/games/*` и `/engine/*`; авторитет и валидация (никнейм, лобби, матч) — на game-server,
в клиенте только рендер и ввод.

## 56. Размер контейнера зависит от количества элементов (лейаут «прыгает»)

**Антипаттерн.** Высота/ширина блока со списком задаётся **интринсиком контента**:
контейнер растёт от нуля по мере добавления элементов (или без ограничения вообще), а
`max-height` лишь ставит потолок. Пустое состояние схлопывает блок в ноль.

**Почему больно.** Лейаут нестабилен: при подгрузке (пагинация/стрим/поиск) контейнер и
весь экран меняют размер и **дёргаются**, скролл-позиция скачет, блоки под списком
уезжают. На разном количестве данных экран выглядит по-разному — невозможно верстать и
тестировать предсказуемо; пустое↔первый элемент даёт «мигание» высоты.

**Как правильно.** Контейнеру с **переменным числом** элементов — стабильный вьюпорт,
не зависящий от count: фиксированная высота из токена (`height: var(--list-h)`) **или**
`flex:1; min-h-0` (занять доступное). Внутри — `overflow-y:auto`. Мало элементов →
пустое место / центрированный empty-state в тех же габаритах; много → скролл **внутри**,
внешний лейаут не двигается. Скроллируемость должна **читаться** (видимый скроллбар +
градиенты у краёв), иначе это выглядит как обрезанный контент (см. §23, §54).

*Иллюстрация:* список лобби в Pardon — рамка фиксированной высоты (`--list-h`) со
скроллом внутри, видимым брасс-скроллбаром и fade-краями; добавление лобби не меняет
высоту экрана.

## TL;DR чек-лист перед коммитом

**Слои (CA):**
- [ ] Бизнес-ветвление не в handler/worker inline — в domain/use case?
- [ ] Handler только: input → use case → serialize/DTO → HTTP?
- [ ] Wire-форма сущности через один билдер, не копипаст dict (§44)?
- [ ] Domain-модуль не импортирует FastAPI/HTTP/Telethon типы ответа?

- [ ] Не добавил ли я голый литерал статуса/типа вместо enum/константы?
- [ ] Не скопировал ли блок, который уже есть (reset/guard/query/условие)?
- [ ] Нет ли комментария «держите в синхроне с X» — не пора ли вынести общий код?
- [ ] Функция < ~100 строк, вложенность < 3, состояние явное (не `nonlocal`)?
- [ ] Ошибки классифицирую по типу, а не по подстроке; неизвестное не глотаю?
- [ ] Тест проверяет поведение, а не текст исходника?
- [ ] Одноразовая миграция не осела в hot-path навсегда?
- [ ] Мёртвый код/импорты убраны (с проверкой re-export и side-effect)?
- [ ] Меняю структуру, а не логику; изменение поведения — отдельно и с подтверждением?
- [ ] Есть baseline тестов и регресс-чек показывает 0 новых падений?

**Бизнес-логика:**
- [ ] Новый статус/состояние: есть ли автоматический путь ВЫХОДА (кто вернёт в работу)?
- [ ] Флаг/исключение заскоуплены на нужную сущность, а не глобально «есть ли хоть один»?
- [ ] Инвариант уникальности/владения enforced структурно (index/lock/claim), а не «на надежде»?
- [ ] Два правила на одну сущность — проверил их пересечение для важного класса?
- [ ] Нет ли окна между commit'ами, где A есть, а согласованного B ещё нет (и никто не чинит)?
- [ ] Посчитанный сигнал реально влияет на решение, а не просто присутствует?
- [ ] Лимит/квота расходуется атомарно ПЕРЕД действием (claim), а не булев гейт по снимку до fan-out?
- [ ] Один провал/успех бампает счётчик ровно один раз (нет double-count на двух ветках)?
- [ ] Heal досводит ВСЕ факты второй фазы (статус + счётчики + тайминги), а не только главный статус?
- [ ] Enforcement инварианта работает на всех бэкендах, а не только за `if dialect == ...`?

**Конкурентность/ресурсы:**
- [ ] Один ресурс — один лок на всё время владения; нет двух локов под разные глаголы на одном id?
- [ ] Кэш ограничен по размеру (LRU/потолок) и/или свипается; keyspace не растёт безгранично?
- [ ] Write-through кэш обновляется ПОСЛЕ commit, а не до (кэш следует за БД, не опережает)?
- [ ] Backoff — один хелпер с jitter, а не N ручных копий с разной базой и без рандомизации?
- [ ] Нет блокирующего I/O и `threading.Lock` в async-пути (только `to_thread`/`asyncio.Lock`)?
- [ ] Ресурс, захваченный до `return`, освобождается на error-пути (`try/except: release; raise`)?
- [ ] Ключ shared-кэша включает всю identity (session/account/tenant), от которой зависит значение?
- [ ] Safety-critical константа клампится жёстким минимумом, как соседи (нельзя выключить в 0)?
- [ ] Два предиката на одну колонку не гасят друг друга; каждая спроектированная ветка достижима?

**API / HTTP:**
- [ ] Имя из запроса не идёт в `getattr(Model, ...)` без allow-list?
- [ ] Мутирующий эндпоинт идемпотентен (set целевого состояния, не toggle/дельта)?
- [ ] Export/aggregate имеет верхний потолок строк (не `.all()` по всей таблице)?
- [ ] «Latest per group» — window/limit в SQL, не full history + dict dedupe (§51)?
- [ ] Наружу не уходит `str(e)`; сырой текст исключения — только в лог?
- [ ] Нет N+1 в цикле по коллекции, если есть batch-хелпер?
- [ ] Auth/сквозной концерн — на уровне router/middleware, а не построчно в каждом хендлере?
- [ ] Один энтити сериализуется одним билдером, а не N inline-словарями?

**Фронтенд:**
- [ ] `key`/id — стабильный доменный id, а не `Date.now()` (и seq переинициализируется после rehydrate)?
- [ ] Всё, что видит юзер в ленте, — элемент одного упорядоченного массива, ничего «сбоку»?
- [ ] В сторе — данные, а не HTML; нет `dangerouslySetInnerHTML` для модельного текста?
- [ ] Высоты — flex + `dvh`, а не `vh`/`overflow:hidden` на body?
- [ ] На сжимаемых flex-детях стоит `min-w-0`/`min-h-0`; `scrollWidth===innerWidth` на 390px?
- [ ] Токены дизайна — в одном месте; кнопки/чипы/модалки — переиспользуемые примитивы?
- [ ] Ширины/отступы/радиусы — из шкалы токенов (`--control-w`/`--stack-gap`/…), не хардкод-числа; контролы в стопке не слипаются, между ними `--stack-gap` (§54)?
- [ ] Текст залит **сплошным** цветом (нет `background-clip:text`/`text-fill-color:transparent`); градиенты — на поверхностях, не на глифах (§53)?
- [ ] Клиент в прод — собранный бандл (bundle+minify), дерево исходников не монтируется; секретов/авторитета в клиенте нет (обфускация ≠ безопасность) (§55)?
- [ ] Контейнер списка не меняет размер от кол-ва элементов — фикс. высота/`flex:1 min-h-0` + внутренний скролл, скроллируемость видна (§56)?
