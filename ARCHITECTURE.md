# ARCHITECTURE.md

## Points QR

### Выдача QR из личного кабинета
- **Правило**: любой авторизованный пользователь с ролью `passenger`, `driver`, `admin` или `moderator` может создать QR через `POST /api/points/qr/issue`. Роль `driver` не блокирует генерацию из личного кабинета.
- **Почему**: водитель может одновременно быть пользователем приложения и пополнять свой баланс через QR другого водителя.
- **Дата**: 2026-07-08

## Points Transfer

### Перевод поинтов между пользователями
- **Правило**: авторизованный пользователь может перевести поинты другому пользователю по его `user_id` (Telegram ID) через `POST /api/points/transfer` с телом `{ recipientUserId, points }`. Лимит одной операции: 1–10000 pts.
- **Правило**: перевод себе запрещён; получатель должен существовать в таблице `users`; баланс отправителя проверяется атомарно (row lock обоих участников).
- **Правило**: в профиле (`/profile`) каждый пользователь видит свой `user_id` с кнопкой копирования — это ID для получения переводов.
- **Почему**: P2P-перевод без QR/карты; `user_id` = Telegram ID, не username.
- **Дата**: 2026-07-11

## Service Zones

### Сущность и админка
- **Правило**: сервисные зоны — только **полигоны** (`service_zones`), не map marks. Название и цвет (hex) задаются свободно; без хардкода сетей магазинов.
- **Правило**: админ **создаёт** зону кликами по карте (POST): `name`, цвет из пресета, `polygon`, `isActive=true`. Редактирование существующих зон (имя, цвет, контур) в UI **отключено** — только создание, вкл/выкл, удаление и «Показать на карте».
- **Правило**: при рисовании каждая точка видна на карте (маркер с номером); кастомный hex при создании недоступен — только пресеты `ZONE_COLORS`.
- **Правило**: клик по зоне на карте открывает вкладку Zones в сайдбаре, выделяет зону и скроллит к её карточке; в списке зон есть поиск по названию.
- **Дата**: 2026-07-11 (обновлено 2026-07-14)

### Pickup-only (точка A / from)
- **Правило**: если есть **активные** зоны, точка посадки (`from_lat/lng`) должна попадать в одну из них. Бэкенд при создании/изменении pickup **отклоняет** точку вне зон ответом HTTP `400` с `detail={"code": "pickup_out_of_zone", "message": ...}` — координаты никогда не «притягиваются» к центроиду зоны (`snap_pickup_coordinates` оставлен как no-op для совместимости).
- **Правило**: точка высадки (`to`) **никогда** не проверяется зонами — ни на бэкенде, ни в UI подтверждения.
- **Правило**: если активных зон нет — ограничений нет (как раньше).
- **Почему**: зоны моделируют парковки/посадку у магазинов; высадка произвольная; пользователь не видит полигоны на карте. Молчаливый snap менял адрес заказа за спиной пользователя, поэтому выбран отказ.
- **Дата**: 2026-07-11 (обновлено 2026-09-30)

### UX пассажира и водителя
- **Правило**: полигоны зон **не показываются** на карте пассажира/водителя. Пин остаётся там, куда поставил пользователь; точка A вне активных зон не подтверждается и не «телепортируется» в зону — показывается подсказка о зоне обслуживания, а создание заявки/оффера бэкенд отклоняет (`pickup_out_of_zone`).
- **Дата**: 2026-07-14 (обновлено 2026-09-30)

## Admin Settings

### Инфо для главного экрана (`userInfoText`)
- **Правило**: текст редактируется в Settings → «Инфо для главного экрана», сохраняется через `PATCH /api/pricing`. Пока админ редактирует несохранённый черновик, polling админки (10 с) **не перезаписывает** поля — только после Save или если черновик совпадает с сервером.
- **Дата**: 2026-07-14

### Свёртка левой панели (desktop)
- **Правило**: на desktop (≥769px) свёрнутое состояние полностью скрывает сайдбар, включая icon rail; раскрытие — кнопкой `>` на карте. На mobile по-прежнему peek-drawer (~56px снизу).
- **Почему**: slim rail при «свёрнуто» конфликтовал с ожиданием полной карты; expand-кнопка на карте уже есть.
- **Дата**: 2026-07-17

## Driver Passenger Order

### Постоянный номер после первого одобрения
- **Правило**: при первом одобрении/назначении пассажира водителем пассажиру присваивается следующий порядковый номер в последовательности этого водителя; этот номер больше не меняется и не переиспользуется при переходах поездки, включая посадку, выход и завершение.
- **Правило**: `passengerNumber` — внутренний идентификатор пассажира в интерфейсе водителя (карта, текущая точка, карточка); глобальный `rideNumber` остаётся номером заявки для пассажира, админки и истории. Навигационный `recommendedOrder` вычисляется отдельно и не меняет `passengerNumber`.
- **Почему**: водитель должен узнавать пассажира по одному и тому же номеру на всех стадиях поездки; без отдельной сущности рейса/смены безопасной границы для сброса последовательности нет.
- **Дата**: 2026-07-17

## Driver Notifications

### Назначение поездки администратором
- **Правило**: при admin assign (single и bulk) Telegram-уведомление уходит и пассажиру, и водителю (если у водителя есть связанный `user_id`). Self-claim водителем себя не уведомляет.
- **Почему**: водитель должен узнать о новой назначенной поездке сразу, а не ждать polling кабинета.
- **Дата**: 2026-07-17

## Ride lifecycle: «Еду на точку» / «Прибыл» / ожидание / неявка

### События поездки дублируются в приложение (не только в Telegram)
- **Правило**: каждое событие поездки — назначение, «еду на точку», «прибыл», старт, финиш, отмена, неявка, новое сообщение чата — пишется и в Telegram, и в ленту уведомлений приложения (`notifications`), для пассажира и для водителя.
- **Почему**: раньше события жили только в Telegram, поэтому в мини-аппе пассажир не видел, что водитель уже едет/приехал.
- **Дата**: 2026-10-14

### Чат поездки: водитель + попутчики одной машины
- **Правило**: чат привязан к «машине»: `thread_key = g:<group_id>` для сгруппированных заявок, `g:offer:<offer_id>` для мест одного предложения водителя и `r:<ride_id>` для одиночной. В треде состоят водитель и все пассажиры группы; системные записи (статусы, неявка, «пассажир на месте») остаются в истории поездки.
- **Правило**: чат живёт только в мини-аппе; сообщения не пересылаются в Telegram-ЛС. В Telegram уходят только уведомления о событиях/новом сообщении со ссылкой обратно в приложение, чтобы не подменять групповой чат личной перепиской с ботом.
- **Правило**: писать можно только пока поездка активна (`assigned`…`in_progress`); после завершения/отмены — чтение без отправки; лимит 20 сообщений в минуту; «Где вы?» — раз в 3 минуты.
- **Правило**: заблокированные друг с другом участники не могут писать друг другу.
- **Дата**: 2026-10-19

### Водитель не закрыл поездку: вопрос «Поездка состоялась?»
- **Правило**: если поездка остаётся `in_progress` дольше «расчётное время в пути × `RIDE_COMPLETION_CHECK_FACTOR` (2)» (оценка: `quote_duration_min` → `quote_road_km` → прямая дистанция → fallback; границы `..._MIN_MINUTES` / `..._MAX_MINUTES`), сторож отправляет пассажиру вопрос «Поездка состоялась?» — карточка в приложении с кнопками [Да]/[Нет] и inline-кнопки в Telegram.
- **Правило**: «Да» закрывает поездку от имени пассажира (журнал `ride_status_events`: actor `passenger`), водитель получает уведомление; «Нет» оставляет `in_progress`, но помечает поездку `passenger_not_completed` и уведомляет администраторов; молчание дольше `RIDE_COMPLETION_CHECK_ESCALATE_MINUTES` (60 мин) → пометка `completion_unconfirmed` и админ-контроль.
- **Правило**: вопрос задаётся один раз, ответы идемпотентны (повторный клик/ответ из второго канала ничего не меняет), после ответа кнопки исчезают у всех участников.
- **Почему**: закрывает жалобу «водитель начал поездку и не нажал Завершил — статус висит вечно, пассажир не знает, состоялась ли поездка».
- **Дата**: 2026-10-14

### Статусы: идемпотентность, откат, защита от «рано» и неявка
- **Правило**: повторное нажатие («Прибыл» дважды, второе устройство, двойной тап) — не ошибка и не дублирует уведомления.
- **Правило**: «Еду на точку» нельзя отметить раньше чем за `RIDE_EN_ROUTE_MAX_EARLY_MINUTES` (360 мин) до подачи — иначе пассажир ждёт напрасно.
- **Правило**: ошибочный шаг откатывается в окне `RIDE_STATUS_UNDO_WINDOW_MINUTES` (5 мин); откат не отправляет Telegram, только запись в приложении и чате.
- **Правило**: неявку («пассажир не вышел») оформляют только после «Прибыл» и `RIDE_NO_SHOW_MIN_WAIT_MINUTES` (5 мин) ожидания; пассажиру уходит объяснение, админам — уведомление. Ожидание можно один раз продлить (`RIDE_WAIT_EXTENSION_MINUTES`), после `RIDE_MAX_WAIT_MINUTES` сторож закрывает поездку как неявку.
- **Правило**: старт поездки — строго после «Прибыл», не раньше `RIDE_START_MAX_EARLY_MINUTES` до назначенного времени; если пассажир не подтвердил посадку, действует `RIDE_START_MIN_WAIT_MINUTES`.
- **Правило**: пассажир может подтвердить посадку (`passenger_boarded_at`); в первые `RIDE_START_DISPUTE_WINDOW_MINUTES` после старта доступна кнопка «Поездка не начиналась» — отмена с полным возвратом и разбором администратора.
- **Правило**: деньги при бронировании — эскроу. Ранняя отмена пассажира и отмена водителем/админом дают полный возврат; поздняя отмена и неявка удерживают `RIDE_PASSENGER_LATE_CANCEL_FEE_PERCENT` / `RIDE_NO_SHOW_FEE_PERCENT` в пользу водителя. Возврат идемпотентен по `reference_id` поездки.
- **Правило**: если водитель не выехал/не приехал, сторож авто-отменяет поездку с полным возвратом (`RIDE_DRIVER_LATE_AUTO_CANCEL_MINUTES`, `RIDE_EN_ROUTE_AUTO_CANCEL_MINUTES`); зависшая `in_progress` закрывается через `RIDE_DISPUTE_AUTO_CLOSE_MINUTES` без повторного списания.
- **Правило**: фоновый сторож (`ride_watchdog`, раз в минуту) напоминает пассажиру о водителе, подсказывает водителю про неявку и помечает «зависшие» поездки как требующие внимания администратора.
- **Почему**: закрывает реальные жалобы — «водитель уехал через 10 секунд», «пассажир спустился, а машины нет», «статус завис, никто не знает где водитель», «нажал кнопку по ошибке».
- **Дата**: 2026-10-14
