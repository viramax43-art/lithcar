# ARCHITECTURE.md

## Points QR

### Выдача QR из личного кабинета
- **Правило**: любой авторизованный пользователь с ролью `passenger`, `driver`, `admin` или `moderator` может создать QR через `POST /api/points/qr/issue`. Роль `driver` не блокирует генерацию из личного кабинета.
- **Почему**: водитель может одновременно быть пользователем приложения и пополнять свой баланс через QR другого водителя.
- **Дата**: 2026-07-08

## Points Transfer

### Перевод поинтов между пользователями
- **Правило**: авторизованный пользователь может перевести поинты другому пользователю по его `user_id` (Telegram ID) через `POST /api/points/transfer` с телом `{ recipientUserId, points }`. Лимит одной операции: 1–10000 pts.
- **Правило**: перевод себе запрещён; получатель должен существовать в таблице `users`; баланс отправителя проверяется атомарно (row lock обоих участников).
- **Правило**: в профиле (`/profile`) каждый пользователь видит свой `user_id` с кнопкой копирования — это ID для получения переводов.
- **Почему**: P2P-перевод без QR/карты; `user_id` = Telegram ID, не username.
- **Дата**: 2026-07-11

## Service Zones

### Сущность и админка
- **Правило**: сервисные зоны — только **полигоны** (`service_zones`), не map marks. Название и цвет (hex) задаются свободно; без хардкода сетей магазинов.
- **Правило**: админ **создаёт** зону кликами по карте (POST): `name`, цвет из пресета, `polygon`, `isActive=true`. Редактирование существующих зон (имя, цвет, контур) в UI **отключено** — только создание, вкл/выкл, удаление и «Показать на карте».
- **Правило**: при рисовании каждая точка видна на карте (маркер с номером); кастомный hex при создании недоступен — только пресеты `ZONE_COLORS`.
- **Правило**: клик по зоне на карте открывает вкладку Zones в сайдбаре, выделяет зону и скроллит к её карточке; в списке зон есть поиск по названию.
- **Дата**: 2026-07-11 (обновлено 2026-07-14)

### Pickup-only (точка A / from)
- **Правило**: если есть **активные** зоны, точка посадки (`from_lat/lng`) должна попадать в одну из них. Бэкенд при создании/изменении pickup **не отклоняет** точку вне зоны — **snap** к centroid ближайшей активной зоны (`snap_pickup_coordinates`).
- **Правило**: точка высадки (`to`) **никогда** не проверяется зонами — ни на бэкенде, ни в UI подтверждения.
- **Правило**: если активных зон нет — ограничений нет (как раньше).
- **Почему**: зоны моделируют парковки/посадку у магазинов; высадка произвольная; пользователь не видит полигоны на карте.
- **Дата**: 2026-07-11 (обновлено 2026-07-14)

### UX пассажира и водителя
- **Правило**: полигоны зон **не показываются** на карте пассажира/водителя. Пин остаётся там, куда поставил пользователь; при подтверждении точки A координаты snap к ближайшей зоне. Пока пин вне зоны — подсказка «Вы можете заказать посадку отсюда».
- **Дата**: 2026-07-14

## Admin Settings

### Инфо для главного экрана (`userInfoText`)
- **Правило**: текст редактируется в Settings → «Инфо для главного экрана», сохраняется через `PATCH /api/pricing`. Пока админ редактирует несохранённый черновик, polling админки (10 с) **не перезаписывает** поля — только после Save или если черновик совпадает с сервером.
- **Дата**: 2026-07-14

### Свёртка левой панели (desktop)
- **Правило**: на desktop (≥769px) свёрнутое состояние полностью скрывает сайдбар, включая icon rail; раскрытие — кнопкой `>` на карте. На mobile по-прежнему peek-drawer (~56px снизу).
- **Почему**: slim rail при «свёрнуто» конфликтовал с ожиданием полной карты; expand-кнопка на карте уже есть.
- **Дата**: 2026-07-17

## Driver Passenger Order

### Постоянный номер после первого одобрения
- **Правило**: при первом одобрении/назначении пассажира водителем пассажиру присваивается следующий порядковый номер в последовательности этого водителя; этот номер больше не меняется и не переиспользуется при переходах поездки, включая посадку, выход и завершение.
- **Правило**: `passengerNumber` — внутренний идентификатор пассажира в интерфейсе водителя (карта, текущая точка, карточка); глобальный `rideNumber` остаётся номером заявки для пассажира, админки и истории. Навигационный `recommendedOrder` вычисляется отдельно и не меняет `passengerNumber`.
- **Почему**: водитель должен узнавать пассажира по одному и тому же номеру на всех стадиях поездки; без отдельной сущности рейса/смены безопасной границы для сброса последовательности нет.
- **Дата**: 2026-07-17
